크롬 북마크 데이터 구조 및 로컬 저장 구조
(수정판 · 2026-10-06 · 기능명세·API명세 v10과 프로토타입 검증 결과, 10월 6일 확정 규칙 반영)

1. 전체 구조

이번 확장 프로그램은 Chrome이 실제로 관리하는 북마크 데이터와 확장 프로그램에서 기능을 제공하기 위해 추가로 관리하는 사용자 데이터를 분리하여 구성한다.

전체적인 데이터 흐름은 다음과 같다.

Chrome 북마크 데이터
↓
chrome.bookmarks API를 이용하여 북마크 정보 조회 및 변경
↓
확장 프로그램에서 북마크 상태 및 사용자 행동 확인
↓
정리 기록 / 직접 옮김 / 새 북마크 / 다시 안 볼 북마크 / 최근 열람 시간 / 고정 목록 관리
↓
chrome.storage.local에 확장 프로그램 전용 데이터 저장

Chrome의 북마크는 폴더와 북마크가 트리 형태로 구성되며, 각 항목은 BookmarkTreeNode 형태로 관리된다. 확장 프로그램에서는 chrome.bookmarks API를 통해 이러한 데이터를 조회하거나 생성·수정·이동할 수 있다.

반면 chrome.storage.local은 Chrome 북마크 자체를 저장하는 공간이 아니라, 우리 확장 프로그램이 기능을 제공하기 위해 필요한 별도의 사용자 관리 데이터를 저장하는 공간으로 사용한다. storage.local의 데이터는 각 머신에 로컬로 저장된다.

확장 프로그램은 두 부분으로 나뉘어 이 데이터를 다룬다.

새 탭 화면: 새 탭이 열려 있을 때만 동작한다. 화면을 그리고, 정리와 되돌리기를 실행한다.
서비스 워커: 새 탭이 닫혀 있어도 동작한다. 북마크가 새로 저장되거나 이동·삭제되는 것을 받아 기록한다.

2. Chrome 북마크 데이터
chrome.bookmarks

Chrome에서 실제로 관리하는 원본 북마크 데이터이다.

확장 프로그램에서는 이 데이터를 직접 별도의 DB에 복사하여 관리하는 것이 아니라, Chrome의 북마크 API를 통해 현재 북마크 상태를 가져온다.

주요 데이터
데이터   의미   용도
id   북마크 또는 폴더의 고유 ID   특정 북마크 식별
parentId   해당 항목이 속한 상위 폴더의 ID   폴더 구조 파악
index   같은 폴더 안에서의 위치   북마크 순서 확인, 되돌리기
title   북마크 또는 폴더의 이름   화면에 이름 표시, 분류, 검색
url   북마크가 연결되는 주소 (폴더에는 없음)   실제 페이지 이동, 분류
children   폴더 내부의 하위 항목 (폴더에만 있음)   폴더 구조 파악
dateAdded   북마크가 추가된 시간   "새로" 표시, 오래된 북마크 판단
dateLastUsed   Chrome 북마크 화면에서 마지막으로 연 시간 (한 번도 안 열었으면 없음)   마지막으로 연 시점 판단, 요즘 쓰는 북마크 보호
folderType   최상위 폴더의 종류 (bookmarks-bar, other, mobile)   북마크바·기타 북마크·모바일 북마크 구별, 새 폴더를 만들 위치(북마크바) 찾기
syncing   계정과 동기화되는 폴더인지   같은 종류의 폴더가 두 개로 보일 때 한쪽 고르기

실제 Chrome의 북마크 API에서도 북마크는 트리 구조로 관리되며 id, parentId, index, title, url 등의 속성을 사용한다. 폴더는 url이 없고 children을 통해 하위 항목을 가진다.

주의할 점
dateLastUsed는 북마크바나 북마크 관리자에서 열 때만 바뀐다. 주소창에 직접 입력하거나, 링크를 누르거나, 우리 새 탭에서 열 때는 바뀌지 않는다. (실제 크롬에서 확인)
이 성질을 이용해, 북마크바에 있는 북마크 중 dateLastUsed가 최근 30일 안인 것은 "요즘 쓰는 북마크"로 보고 정리 대상에서 뺀다. 따로 저장하는 값은 없다.
북마크바·기타 북마크·모바일 북마크는 폴더 ID가 아니라 folderType으로 구별한다. 로그인하지 않은 크롬에는 모바일 북마크 폴더가 없다.
dateGroupModified는 폴더에만 있는 값이고 우리 서비스에서는 쓰지 않는다.

예시
북마크바
 ├─ 공부
 │   ├─ 네이버
 │   └─ 구글
 │
 └─ 게임
     ├─ Steam
     └─ YouTube

이러한 구조를 그대로 이용하기 때문에 확장 프로그램이 북마크를 정리하면 실제 Chrome의 폴더와 북마크가 변경된다.

확장 프로그램이 Chrome 북마크를 바꾸는 경우는 다음뿐이다.

사용자가 [정리하기]를 눌렀을 때: 북마크바 맨 뒤에 폴더를 만들고, 북마크바와 기타 북마크에 흩어진 북마크를 옮긴다.
사용자가 [되돌리기]를 눌렀을 때: 북마크를 원래 위치로 옮긴다.
사용자가 폴더를 만들거나, 이름을 바꾸거나, 지우거나, 북마크를 직접 옮겼을 때

확장 프로그램은 북마크 자체를 삭제하지 않는다. 폴더를 지울 때도 안의 북마크는 상위 폴더로 꺼낸다.

즉,

chrome.bookmarks = 실제 북마크의 원본 데이터

라고 볼 수 있다.

3. 확장 프로그램에서 별도로 관리하는 데이터

Chrome의 기본 북마크 정보만으로는 우리 서비스에서 필요한 정보를 모두 표현하기 어렵다.

예를 들어 Chrome에는

이 북마크를 우리가 언제 자동 정리했는지
사용자가 직접 옮긴 북마크인지
지금 옮기는 것이 우리 정리인지 사용자인지
새로 저장되어 아직 정리하지 않은 북마크인지
사용자가 다시 보지 않기로 했는지
우리 새 탭에서 마지막으로 언제 열었는지
사용자가 고정한 북마크인지
첫 정리 제안을 이미 봤는지

와 같은 서비스 전용 상태 정보가 없다.

따라서 이러한 데이터는 chrome.storage.local에 별도로 저장한다. 저장 항목은 모두 9개다.

4. 정리 기록 (history)
목적

확장 프로그램의 자동 정리 기능으로 북마크의 위치가 변경되었을 때, 변경 전과 변경 후의 정보를 기록한다.

저장할 정보 (정리 한 번이 기록 한 건)
정리 날짜
정리 종류 (첫 정리 / 새 북마크 정리)
옮긴 북마크마다: 북마크 ID, 제목, 정리 전 폴더, 정리 전 순서, 정리 후 폴더
정리 직전 원래 폴더의 전체 순서 (북마크 ID 목록)
그 정리가 새로 만든 폴더 목록
되돌린 시각 (되돌리지 않았으면 비어 있음)

정리 이유(왜 그 폴더에 넣었는지)는 저장하지 않는다.

각 정보가 필요한 이유
제목: 북마크가 나중에 삭제되어도 정리 기록 화면에 이름을 보여 주기 위해서다.
원래 폴더의 전체 순서: 되돌릴 때 "원래 바로 앞에 있던 북마크의 뒤"에 놓기 위해서다. 순서 번호만으로 되돌리면, 그사이 다른 북마크가 빠지거나 추가됐을 때 순서가 뒤섞인다. (프로토타입에서 확인)
새로 만든 폴더 목록: 되돌린 뒤 비게 된 폴더를 지우기 위해서다. 원래 있던 폴더는 지우지 않는다.
원래 순서는 첫 북마크를 옮기기 전에 한꺼번에 읽어 둔다. 옮기면서 하나씩 읽으면 번호가 당겨져 틀린 값이 저장된다.

사용되는 기능

① 정리 기록 화면

사용자가 이전에 어떤 북마크가 어떻게 정리되었는지 확인할 수 있다.

② 되돌리기(Undo)

정리하기 전의 위치 정보를 이용하여 북마크를 이전 위치로 되돌릴 수 있다. 정리 뒤에 사용자가 직접 옮긴 북마크와 삭제된 북마크는 건드리지 않는다.

중요한 구분

확장 프로그램의 정리 기능으로 이동된 경우에는 정리 기록으로 관리한다.

반대로 사용자가 직접 이동한 경우에는 아래의 직접 옮긴 북마크로 별도로 관리한다.

5. 직접 옮긴 북마크 (manualMoves)

사용자가 직접 북마크를 이동한 경우 이를 기록한다.

사용자가 직접 이동했다는 사실을 기억하는 이유는 다음 자동 정리에서 해당 북마크를 다시 이동시키지 않기 위해서이다.

저장할 정보
북마크 ID
옮긴 시각

옮긴 위치는 저장하지 않는다. 지금 위치는 Chrome이 알고 있다.

예시
사용자가
"네이버"를
[공부] 폴더 → [자주 보는 것] 폴더로 직접 이동

        ↓

직접 옮긴 북마크로 기록

        ↓

다음 자동 정리 실행

        ↓

"네이버"는 자동 정리 대상에서 제외

누가 기록하는가

서비스 워커가 기록한다. 사용자는 새 탭이 닫혀 있을 때도 Chrome 북마크 관리자에서 북마크를 옮길 수 있기 때문이다. 우리 새 탭에서 우클릭이나 드래그로 옮긴 것도 같은 방식으로 서비스 워커가 기록한다.

같은 폴더 안에서 순서만 바꾼 것은 직접 옮김으로 기록하지 않는다.

따라서 이 데이터는 단순한 이동 기록이라기보다는,

사용자가 직접 정한 북마크 위치를 자동 정리 기능이 다시 변경하지 않도록 하기 위한 기억 데이터

라는 의미가 있다.

6. 옮기는 중 표시 (pendingMoves)
목적

Chrome은 북마크가 옮겨졌다는 것만 알려 주고, 누가 옮겼는지는 알려 주지 않는다. 그래서 우리 정리가 옮긴 것과 사용자가 직접 옮긴 것을 구별하려면 표시가 필요하다.

저장할 정보
북마크 ID
옮길 목적지 폴더
표시한 시각

동작 과정
정리(또는 되돌리기) 시작
        ↓
옮길 북마크와 목적지를 먼저 저장 (저장이 끝날 때까지 기다림)
        ↓
북마크를 옮김
        ↓
서비스 워커가 이동 알림을 받음
        ↓
같은 북마크, 같은 목적지가 1분 안에 표시되어 있으면 → 우리 정리 (기록하지 않음)
표시가 없으면 → 직접 옮긴 북마크로 기록

표시는 옮긴 뒤에 지우지 않고 1분이 지나면 만료시킨다. 옮긴 직후에 지우면 서비스 워커가 알림을 받기 전에 표시가 사라져, 우리 정리가 전부 "직접 옮김"으로 잘못 기록되고 되돌리기가 막힌다. (실제 크롬에서 확인)

7. lastOpenedByUs
목적

확장 프로그램의 새 탭에서 사용자가 북마크를 열었을 때 마지막으로 열었던 시간을 기록한다.

이 정보는 특히 「잊고 있던 북마크」 기능에서 사용한다.

저장할 정보
북마크 ID
마지막으로 연 시각

동작 과정
사용자가 새 탭에서 북마크 클릭
        ↓
현재 시간을 lastOpenedByUs에 저장
        ↓
북마크 열림
왜 별도로 저장하는가?

Chrome의 dateLastUsed는 북마크바나 북마크 관리자에서 열 때만 바뀌고, 우리 새 탭에서 열 때는 바뀌지 않는다. 그래서 우리 화면에서 연 시각은 우리가 직접 적어 두어야 한다.

「잊고 있던 북마크」를 판단할 때 마지막으로 연 시각은 다음과 같이 정한다.

lastOpenedByUs와 Chrome의 dateLastUsed 중 더 최근 값
둘 다 없으면 dateAdded

"lastOpenedByUs가 있으면 그것만 쓴다"가 아니다. 우리 새 탭에서 두 달 전에 열고 어제 북마크바에서 다시 연 북마크를 "두 달 안 연 것"으로 잘못 판단하지 않기 위해서다.

알려진 한계
주소창에 직접 입력해서만 여는 북마크는 어느 쪽에도 기록이 남지 않아 "안 연 것"으로 보일 수 있다. 사용자는 「이제 안 봐도 됨」으로 뺄 수 있다. 그래서 화면에는 "안 열어 봄"이 아니라 "연 기록 없음"이라고 쓴다.

8. 다시 안 볼 북마크 (dismissed)

사용자가 북마크를 확인한 뒤 「이제 안 봐도 됨」으로 지정하면 해당 북마크를 별도로 기록한다.

목적

사용자가 더 이상 필요하지 않다고 판단한 북마크를 「잊고 있던 북마크」 후보에서 제외하기 위해서다.

저장할 정보
북마크 ID
지정한 시각

흐름
사용자가 북마크 확인
        ↓
"이제 안 봐도 됨" 선택
        ↓
해당 북마크 ID 저장
        ↓
앞으로 해당 북마크를
다시 추천/표시하지 않음

즉, 이 데이터는 북마크 자체를 삭제하는 것이 아니다.

Chrome의 실제 북마크는 그대로 유지하면서,

우리 확장 프로그램에서 다시 보여주지 않도록 상태만 별도로 저장

하는 방식이다.

9. 고정 목록 (pinned)

사용자가 자주 사용하는 북마크를 새 탭의 고정 영역(독, 화면 아래에 떠 있음)에 표시하기 위한 데이터이다.

저장할 정보
북마크 ID의 목록 (목록의 순서가 곧 표시 순서)

최대 8개까지 고정한다. 고정해도 Chrome 북마크의 위치는 바뀌지 않는다.

흐름
사용자가 북마크 고정
        ↓
북마크 ID 저장
        ↓
새 탭의 고정 영역에 표시

고정된 북마크는 사용자가 자주 사용하는 것으로 판단할 수 있기 때문에 「잊고 있던 북마크」 후보에서도 제외한다.

즉,

고정 = 사용자가 현재도 자주 사용하는 북마크

로 취급하여 불필요한 추천이나 알림을 방지한다.

10. 새 북마크 (newBookmarks, handledNew)
목적

사용자가 새로 저장한 북마크에 "새로" 표시를 붙이고, [정리하기 · N] 버튼에 개수를 보여 주기 위한 데이터이다.

newBookmarks: 폴더 밖에 새로 저장되고 아직 옮기지 않은 북마크의 ID 목록
handledNew: 새 북마크 중 [정리하기]에서 "그대로 두기"로 둔 북마크의 ID 목록

화면에 "새로"로 보이는 북마크 = newBookmarks에서 handledNew를 뺀 것

동작 과정
사용자가 별 버튼으로 북마크 저장
        ↓
북마크바·기타 북마크·모바일 북마크 바로 아래에 저장됐으면
서비스 워커가 newBookmarks에 추가
(폴더를 지정해 저장한 북마크는 추가하지 않음)
        ↓
새 탭에 "새로" 표시, [정리하기 · N]
        ↓
정리해서 폴더로 옮기면 → 서비스 워커가 newBookmarks에서 제거
"그대로 두기"로 두면 → 새 탭이 handledNew에 추가

두 개로 나눈 이유는 newBookmarks는 서비스 워커만, handledNew는 새 탭만 쓰게 하기 위해서다. (14번의 규칙)

11. 첫 정리 카드 상태 (state)

설치 후 처음 새 탭을 열었을 때 보여 주는 첫 정리 카드를 이미 처리했는지 기억한다.

저장할 정보
첫 정리 카드 상태: 대기(pending) / 완료(done) / 나중에(later)

이 값이 없으면 새 탭을 열 때마다 첫 정리 카드가 다시 뜬다. "나중에"인 동안에는 헤더의 [정리하기] 버튼으로 카드를 다시 열 수 있다.

12. 「잊고 있던 북마크」와 저장 데이터의 관계

「잊고 있던 북마크」는 Chrome에 실제 폴더를 만드는 기능이 아니다.

새 탭 화면에서만 보여주는 UI상의 가상 분류이다.

후보를 판단할 때 다음 조건을 사용한다.

후보가 될 수 있는 경우
마지막으로 열어본 지 30일 이상 지난 북마크
제외되는 경우
저장한 지 7일이 지나지 않은 북마크
고정된 북마크
「이제 안 봐도 됨」으로 지정한 북마크
javascript: 주소
chrome:// 주소

그리고 마지막으로 연 시각은 7번에서 정한 대로 확인한다.

lastOpenedByUs와 dateLastUsed 중 더 최근 값
      ↓ 둘 다 없으면
dateAdded

후보가 여러 개라면 가장 오래 열어보지 않은 북마크부터 표시한다.

화면에는 한 번에 8개까지만 보여 준다. 하나를 열거나, 고정하거나, 「이제 안 봐도 됨」으로 지정하면 다음 후보가 올라온다. 설치 첫날에는 주소창으로 여는 북마크까지 대부분 후보가 되기 때문이다. 8개라는 숫자는 저장하지 않고 화면에서 자른다.

따라서 「잊고 있던 북마크」는 하나의 저장 데이터가 아니라,

Chrome 북마크 데이터 + lastOpenedByUs + 고정 목록 + 다시 안 볼 목록 등을 조합하여 화면에서 동적으로 만들어지는 분류

라고 이해하면 된다.

13. chrome.storage.local에 저장되는 데이터 정리

최종적으로 chrome.storage.local에는 다음 9개의 서비스 전용 데이터가 들어간다.

저장 항목   이름   형태   쓰는 쪽   저장 목적
정리 기록   history   기록의 목록   새 탭   자동 정리 전후의 위치를 저장하고 기록 확인 및 Undo에 사용
직접 옮긴 북마크   manualMoves   { 북마크ID: 시각 }   서비스 워커   사용자가 직접 이동한 북마크를 기억하여 다음 자동 정리에서 제외
옮기는 중 표시   pendingMoves   { 북마크ID: { 목적지, 시각 } }   새 탭   우리 정리의 이동과 사용자의 직접 이동을 구별 (1분 뒤 만료)
새 북마크   newBookmarks   [북마크ID, …]   서비스 워커   폴더 밖에 새로 저장된 북마크를 기억
그대로 둔 새 북마크   handledNew   [북마크ID, …]   새 탭   "그대로 두기"로 둔 새 북마크를 기억
lastOpenedByUs   lastOpenedByUs   { 북마크ID: 시각 }   새 탭   새 탭에서 마지막으로 북마크를 연 시간을 기록
다시 안 볼 북마크   dismissed   { 북마크ID: 시각 }   새 탭   사용자가 더 이상 추천받지 않도록 지정한 북마크를 기억
고정 목록   pinned   [북마크ID, …] (최대 8개)   새 탭   새 탭의 고정 영역에 표시할 북마크를 기억
첫 정리 카드 상태   state   { firstCard: 상태 }   새 탭   첫 정리 카드를 처리했는지 기억

정리 기록 한 건의 형태
{ id, at, type, createdFolderIds, moves: [{ bookmarkId, title, fromParentId, fromIndex, toParentId }], fromOrder: { 원래 폴더ID: [북마크ID, …] }, skipped, undoneAt }

Chrome 공식 문서에서도 chrome.storage는 확장 프로그램이 사용자 데이터와 상태를 저장하고 변경 사항을 추적하기 위한 API이며, storage.local은 각 머신에 로컬로 저장되는 저장 영역이다.

14. 저장할 때 지키는 규칙

① 한 항목은 한쪽만 쓴다.

새 탭과 서비스 워커가 같은 항목을 동시에 고치면 한쪽 값이 사라진다. 실제로 양쪽에서 120번 썼더니 91개만 남았다. 그래서 항목마다 쓰는 쪽을 하나로 정했다. (13번 표의 "쓰는 쪽")

② 북마크 원본은 저장하지 않는다.

저장하는 것은 북마크 ID와 시각뿐이다. 제목과 주소는 Chrome에서 그때그때 읽는다. 예외는 정리 기록의 제목 하나로, 기록 화면에 보여 주기 위한 것이다.

③ 북마크 ID는 이 PC에서만 유효하다.

같은 북마크도 다른 PC에서는 ID가 다르다. 그래서 이 데이터는 다른 기기와 동기화하지 않는다.

④ 북마크가 삭제되면 저장 항목에서도 지운다.

서비스 워커는 자기가 쓰는 항목(manualMoves, newBookmarks)에서 바로 지우고, 새 탭은 열릴 때 자기가 쓰는 항목에서 지운다. 정리 기록은 지우지 않는다.

⑤ 모든 저장은 store.js를 거친다.

다른 파일에서 chrome.storage를 직접 부르지 않는다.

15. 전체 데이터 관계

결국 이 구조의 핵심은 두 종류의 데이터를 분리하는 것이다.

① Chrome이 관리하는 실제 북마크
chrome.bookmarks
│
├─ 북마크
├─ 폴더
├─ 폴더 간 관계
├─ 북마크 위치
└─ 북마크 주소
② 우리 확장 프로그램이 관리하는 사용자 상태
chrome.storage.local
│
├─ 정리 기록 (history)
├─ 직접 옮긴 북마크 (manualMoves)
├─ 옮기는 중 표시 (pendingMoves)
├─ 새 북마크 (newBookmarks)
├─ 그대로 둔 새 북마크 (handledNew)
├─ lastOpenedByUs
├─ 다시 안 볼 북마크 (dismissed)
├─ 고정 목록 (pinned)
└─ 첫 정리 카드 상태 (state)

따라서 Chrome 북마크 데이터 자체와 확장 프로그램의 관리 데이터가 섞이지 않는다.

16. 팀원이 구현할 때 이해해야 할 핵심

이 구조에서 가장 중요한 부분은 다음과 같다.

북마크 자체는 chrome.bookmarks가 관리하고,
우리 서비스만 알고 있어야 하는 사용자 행동 및 상태 정보는 chrome.storage.local이 관리한다.

예를 들어 사용자가 북마크를 자동 정리하면 실제 북마크의 위치는 chrome.bookmarks를 통해 변경하고, 변경 전후의 정보는 chrome.storage.local의 정리 기록에 저장한다.

반대로 사용자가 직접 북마크를 이동하면 Chrome의 북마크 위치가 변경되는 것과 별개로, "이 사용자가 직접 옮겼다"는 사실을 서비스 워커가 chrome.storage.local에 기록하여 다음 자동 정리에서 해당 북마크를 보호한다.

이렇게 하면 Chrome의 실제 북마크 구조와 우리 확장 프로그램의 사용자 관리 데이터가 서로 역할을 나누면서도 연결되는 구조가 된다.

한 줄로 요약하면

chrome.bookmarks = 실제 북마크의 원본 데이터
chrome.storage.local = 우리 확장 프로그램이 북마크를 어떻게 관리하고 보여줄지 판단하기 위한 사용자 상태 데이터

18. 10월 6일 판에서 바뀐 점

저장 항목은 9개 그대로이고, 형태도 바뀌지 않았다. 바뀐 것은 Chrome 북마크를 읽고 바꾸는 규칙이다.

정리 대상에 북마크바를 넣었다. 북마크바와 기타 북마크에 흩어진 북마크를 모두 정리한다 (2번)
새 폴더를 기타 북마크 안이 아니라 북마크바 맨 뒤에 만든다 (2번)
북마크바에서 최근 30일 안에 연 북마크는 정리하지 않는다. dateLastUsed로 판단하며 따로 저장하지 않는다 (2번)
「잊고 있던 북마크」는 화면에 8개까지만 보여 주고, 기록이 없으면 "연 기록 없음"이라고 쓴다 (7, 12번)
코드는 프로토타입을 쓰지 않고 처음부터 새로 만든다. 이 문서의 "프로토타입에서 확인", "실제 크롬에서 확인"은 프로토타입을 돌려서 알아낸 사실이며, 새 코드도 그대로 따른다
저장 항목을 읽고 쓰는 파일은 extension/js/store.js 하나다. 화면 파일(render.js, view/ 아래 4개)은 store.js를 거쳐서만 저장한다 (14번 ⑤)
